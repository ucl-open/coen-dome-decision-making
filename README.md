# coen-dome-decision-making

The audiovisual dome decision-making tasks (localization and discrimination), as an open-rigs project on the lab's shared blocks (lib-open-rigs, [Building Blocks](https://github.com/Coen-Lab/lib-open-rigs/blob/main/docs/articles/building-blocks.md)). It was `ucl-open/av-dome`'s `pip/main-switchover` branch until 13 Nov 2026, moved here with its history (Pip) so production av-dome is never touched. A mouse's experiments recorded as av-dome's switch-over branch before the move count as this workflow's: anything that reads a mouse's history (a stage suggestion, for one) reads both. Only the current format is read: production av-dome's TrialSettings logs, task files without `taskType` and folders named by eartag are not (their readers were deleted on 15 Nov 2026; migrating every mouse's past sessions is planned in its own session).

The rig's hardware is in `C:\Coen-Lab-Local\RigConfigs\<MACHINE-NAME>\rig.yml`, the lab rig model `open_rigs.rigs.lab_rig.LabRig` (start from open-rigs' `rigs\rig-template.yml`).

## Running an experiment

The workflow has no window of its own. app-rig-control launches it with `--property:SubjectId=<lab ID> --property:SessionId=<n>`, and it starts into ready mode: the boards connected, the spouts homed and at that mouse's saved positions, the cameras streaming to the live view, nothing recorded. Set the parameters, send commands, then Go.

| Parameter | Default | |
|-----------|---------|-|
| `TrainingStage` | 4 | Row of the task file's `trainingStages`, 0 to 4; a row past the end of the file's table stops the workflow at Go |
| `SpoutStepSize` | 150 | Motor steps per spout nudge, taken live; declared by DomeHardware's `LickSpoutStage` itself |

The task's own settings are the task file's: app-rig-control writes the file chosen at launch from `config\task*.yml`, with the Experiment page's edits, checked against `src\DataSchemas\ucl_open_coen_dome_decision_making_task.json`, at the path it passes as `TaskPath`, read at Go (it writes the chosen file there at launch too, which the workflow reads at Start for the background noise). From the editor `TaskPath` is `config\task-localization.yml`. `trialWeights` and `repeats.rulesPerType` name each trial type by what it shows (`visual`, `auditory`, `audiovisualCoherent`, `audiovisualConflict`, `neutral`). In discrimination the task files' rows are written for a visual-target mouse (visual trials are the target trials): for an auditory-target mouse, swap the stage's `visual` and `auditory` weights on the form. A discrimination stage that gives the target modality no trials while the other has some is refused at Go, saying so.

Commands, while ready or recording: `RewardLeft` and `RewardRight`, each 2.5 µl on that spout through the valve's calibration (Pip's fixed manual drop), and `LickSpoutStage`'s own (lib-open-rigs'): `SpoutsHome`, `SpoutsIn`, `SpoutsOut`, `SaveSpoutPositions` (to `<rig config>\calibration\LickSpoutPositions\<SubjectId>.csv`) and the nudges `LeftUp`, `LeftDown`, `RightUp`, `RightDown`, `LeftFront`, `LeftBack`, `RightFront`, `RightBack`, `BaseLeft`, `BaseRight`; a nudge moves the spouts at once and changes that mouse's in positions, which `SaveSpoutPositions` keeps for its next experiment.

## A trial

The trial is one state machine on the Harp clock, lib-open-rigs' `TrialLoop` (the same as coen-dome-navigation's), running this task's tested C# rules (`TrialRules` in `TrialLogic.cs`); `TaskLogic` sends each of its events to the hardware. Go reads the task file and checks it once (`CheckTaskAtGo`, in `TaskFile`, building `TrialRules`: the stage in the table, the target modality given trials, the interval at least `drinkSeconds`, `laserToStimulusSeconds` within the shortest interval less Zapit's 0.2 s reply margin (`ZapitTrial.ReplyMarginSeconds`) and no later than the response window, the quiet waits, and with optogenetics a `laserDurationSeconds` short enough for Zapit to be armed for the next trial, and the conditions file), stopping the workflow naming each problem; once the experiment folder exists the spouts are drawn back (on a stage with spout movements) and the loop starts (`RunTrials`), the first trial's interval starting then. Each trial is drawn at the start of its interval, the last outcome plus its timeout (`TrialDraw`: type by the stage's weights, repeats by its rules, the speaker that plays is rig.yml's nearest to the drawn location, its own `itiSeconds`, and with optogenetics a Zapit condition on every trial, the laser off at 0 mW on laser-off trials). It starts at the interval's end less the lead, max(`laserToStimulusSeconds`, 0), or later until the stage's quiet waits hold (`lickQuietSeconds` with both spouts released, a held contact holding the start; the wheel's travel, forward and back added, within `wheelQuietCm` over the last `wheelQuietSeconds`; each counted from the interval's start; all 0, off, in the task files); `Trial` and the status metrics change then. The stimulus comes the lead after the trial start, in every experiment, so with a quiet mouse it lands exactly `itiSeconds` after the interval's start (`quietWaitSeconds` says how much the waits added). With optogenetics, `Zapit` sends a hardware-triggered Zapit the trial's StartStimulus during the interval (`Arm`, or once the last trial's laser and its 0.5 s longest ramp-down have ended; a rig without hardware triggering, test mouse only, gets it at the trigger, as Zapit starts the laser on receipt), the loop checks the reply, and the ZapitTrigger line (Zapit's trigger and the masking light) rises at the stimulus less `laserToStimulusSeconds` (signed: before, with or after the stimulus) and falls `laserDurationSeconds` later, unless the trial was answered first (no laser, and the row logs `laserPowerMw` 0; Pip, 13 Nov 2026); on a hardware-triggered rig a reply not in by then stops the workflow, so Zapit adds no time. The stimulus (`stimulusOnsetTime`, the first clock tick at or after it was due), the grating off `stimulusSeconds` after it (`GratingOff`) and the spouts in `stimulusToSpoutsInSeconds` after it (`SpoutsIn`), outcome or not; the response window `responseDelaySeconds` after it for `responseWindowSeconds`: each lick in it adds 1 (left) or -1 (right) to `DecisionVariable`, the grating moving `degreesPerLick` a lick from its drawn azimuth, and the choice is Left at `thresholdLicks`, Right at -`thresholdLicks`, else NoResponse at the window's end; a lick before the window is not counted. The answer is the trial's target (on coherent and conflict trials the stimuli's, the grating's, side). At the outcome the trial's row is built and its consequence runs (reward at the target, spouts, the lab's penalty sound); then the timeout, and the next interval from its end (`itiStartTime`), the spouts out `drinkSeconds` into it (`Drink`).

## Data

The experiment folder is `<rootPath>\sub-<SubjectId>\ses-<SessionId>_<DateTime>`, with a folder per device, `Settings` (`Settings_Rig_`, `Settings_Task_`, `Settings_Experiment_`), each valve's calibration (`ValveCalibrationDO<n>`), `BonsaiData` and `manifest.json`. `BonsaiData_Trial` has one row per trial, written when the outcome is known (columns and meanings in `schemas\trial-columns.yml`); `BonsaiData_Async` one row per event outside a trial (commands, Go, each reward as `RewardDelivered` with the microlitres delivered). Status reports `trialNumber`, `trainingStage`, `target`, `trialType`, the azimuths, `rewardSizeUl` and `laserCondition`; app-rig-control computes trials, performance and water from the files. Each camera's folder (`Camera-Face`, `Camera-Pupil`, `Camera-Body`) holds an hourly `.mkv` (H.264) with a `.csv` of one row per frame: `harpTime`, `frameId`, `cameraClockNs`, `exposureUs`, `gainDb` (`LogVideoFfmpeg`; the encoder is `videoEncoder` in rig.yml).

Every file's first column is `harpTime`, the row's Harp time; a trial's moments are their own columns, in the block of columns every dome task shares (lib-open-rigs' `open_rigs.rigs.trials`, held by `tests\test_trial_columns.py`). `uv run summarise-experiment <experiment folder>` reads one experiment from its files alone: how the run ended, trials, performance, each response time and outcome-to-next-stimulus interval, and the water asked against the water delivered. It names each problem, exiting 1: trial numbers with a gap, an outcome not `Correct`, `Incorrect` or `NoResponse`, a trial start or a stimulus more than 2 ms from where the task file puts it, a laser trigger more than 2 ms from `laserToStimulusSeconds` before the stimulus, an interval not starting at the last outcome plus its `penaltyTimeoutSeconds`, a timeout without the penalty sound (or the sound without one) when the task has it on, a rewarded trial with no `RewardDelivered`.
